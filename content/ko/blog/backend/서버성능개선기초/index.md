서버 관점에서 처리량과 응답 시간 개선하는 방법

## 1. 병목 지점

- 성능 문제 발생 원인 :  최대 TPS < 트래픽 유입
- 성능 문제 발생 지점 찾는 법 : 시간이 오래 걸리는 작업 식별 → 모니터링 도구 활용 (의심되는 코드 실행 시간 로그로 남겨두는 방식도 도움이 됨)
- 서버 성능 문제는 주로 DB 연동이나 API 연동 과정에서 발생한다.

## 2. 수직 확장과 수평 확장

- **수직 확장 (Scale Up)** : 급한 불 끄기 - CPU/메모리/디스크 등의 자원 증가시킴 (예- 더 빠른 CPU로 바꾸기, 디스크 SSD로 바꾸기)

수직 확장은 즉각적인 효과 얻을 수 있지만, 트래픽 지속적 증가하면 또다시 성능 문제 발생하고, 비용도 많이 듦

- **수평 확장 (Scale Out)** : 서버를 추가로 투입해 TPS를 높이는 방법

로드밸런서 : 사용자 트래픽을 각 서버에 알맞게 분산시킴

1. 정적인 방식 : RR방식 - 클라이언트 요청 서버에 순차 분배 / IP 해시 방식 - IP 주소 해시 값 기반 요청 전달할 서버 결정
2. 동적인 방식 : 트래픽 적은 서버에 요청 보내는 형태

실제 병목 지점 파악하는 것이 중요! DB에 문제 있는 상황에서 DB 서버 늘리면 부하 커지고 악화됨.

즉, DB나 외부 API에 성능 문제 발생하지 않는 범위 내에서만 수평 확장 진행.

## 3. DB 커넥션 풀

- DB 사용 : DB에 연결 → 쿼리 실행 → 연결 종료
- 서버-DB 네트워크 통신 통해 연결 : 네트워크에서 DB 연결 및 종료 시간은 전체 응답 시간에 영향을 줌 → 응답 시간 길어지면 → 전체 처리량 DOWN (트래픽 증가 시 심해짐) ⇒ DB 커넥션 풀로 해결
- DB 커넥션 풀 : DB에 연결된 커넥션 미리 생성해 보관 → 작업 필요 시 풀에서 커넥션 가져와 사용하고 다시 풀에 반환 (이미 연결된 커넥션 재사용 → 응답시간 DOWN)

**DB 커넥션 풀 설정 옵션**

1. 커넥션 풀 크기 (최소 크기, 최대 크기)
2. 풀에 커넥션 없을 때 커넥션 구할 때까지 대기할 시간
3. 커넥션의 유지 시간 (최대 유휴 시간, 최대 유지 시간)

각 설정이 성능과 품질에 어떤 영향을 주는지는 아래에 설명해놓음

## 4.  커넥션 풀 크기

- 커넥션 풀에 미리 생성해둘 커넥션 개수 지정

예) 커넥션 풀 크기 5, 쿼리 실행 시간 1초 

IF, 서버에 6개 요청 들어왔을 땐? ⇒ 5개 요청은 풀에서 커넥션 가져올 수 있지만, 나머지 1개 요청은 다른 커넥션 풀에 반환될 때까지 기다려야함

- 커넥션 풀 크기는 응답 시간과 TPS를 고려해서 지정해야함

예) 커넥션 풀 크기(5) * 한 요청에서 쿼리 실행하는데 걸리는 시간(0.1초) ⇒ 1초에 처리할 수 있는 요청 수(50)

- 커넥션 풀 ⇒ 최소 크기 & 최대 크기 설정 가능
- 트래픽이 적은 시간대 = 최소 크기로 유지 / 트래픽이 높은 시간대 = 최대 크기로 확장
- DB서버의 CPU 사용률이 매우 높을 때(약 80%) 커넥션 풀 크기를 늘리면 DB에 가해지는 부하 커져 쿼리 실행 시간 증가할 수 있음 ⇒ 서버를 수평 확장 진행

## 5. 커넥션 대기 시간

풀에 사용할 수 있는 커넥션 없을 때 커넥션을 얻기 위해 기다릴 수 있는 최대 시간

→ 대기 시간 안에 커넥션 구하지 못하면 DB 연결 실패 에러 발생

- 대기 시간 길어지면 → 응답 시간도 길어짐 ⇒ 즉, 응답 시간이 중요한 서비스는 대기 시간을 짧게 설정 (0.5초~3초)
- 대기 시간이 길어지면 재요청이 발생하면서 동시 트래픽 증가 (서버 부하도 커짐)
- 즉, 대기 시간을 짧게 설정하면 바로 에러를 응답하기 때문에 서버 부하를 일정 수준으로 유지할 수 있음

## 6. 최대 유휴 시간, 유효성 검사, 최대 유지 시간

풀에 있는 커넥션 일정 시간 사용되지 않으면 DB와 연결 끊김

연결 끊김으로 발생하는 에러 방지하는 커넥션 풀의 기능

1. 최대 유휴 시간 지정
2. 유효성 검사 지원

참고) 최대 유휴 시간 & 최대 유지 시간은 무한대로 설정하지 않는 것이 좋다.

- **최대 유휴 시간** : 사용되지 않는 커넥션을 풀에 유지할 수 있는 최대 시간
- **유효성 검사** : 커넥션이 정상적으로 사용할 수 있는 상태인지 여부 확인
- **최대 유지 시간** : 생성된 시점부터 유지되는 시간

## 7. 서버 캐시

DB 서버 확장 없이 응답 시간과 처리량 개선 위해 사용

- 캐시 : (키, 쌍) 값 저장하는 Map과 같은 형태의 데이터 저장소
- 캐시에 데이터 저장 시 동일 데이터를 요청할 때 db가 아닌 캐시에서 데이터 읽어와 응답 가능 → 응답 시간 감소

DB뿐만 아니라 복잡한 계산 결과나 외부 API 연동 결과도 캐시에 보관하여 응답 시간을 줄이는데 활용 가능하다.

## 8. 적중률과 삭제 규칙

- 적중률 :  캐시가 얼마나 효율적으로 사용되는 지 판단하는 지표

적중률(Hit Rate) = 캐시에 존재한 건수 / 캐시에서 조회를 시도한 건수

- 적중률이 높을수록 → DB와의 연동 줄어듦 → 응답 시간 감소, 처리량 증가, DB 부하 감소
- 캐시는 ‘메모리’를 사용하기 때문에 저장할 수 있는 데이터 개수나 크기 제한됨

캐시가 가득 찬 상태에서 새로운 데이터를 캐시에 저장하기 위해 삭제할 대상을 선택하는 규칙

1. LRU (Least Recently Used) : 가장 오래전에 사용된 데이터 제거
2. LFU (Least Frequently Used) : 가장 적게 사용된 데이터 제거
3. FIFO (First In First Out) : 먼저 추가된 데이터를 먼저 삭제
- 오래된 캐시 사용되지 않을 가능성 큼 → 캐시에 유효시간(만료시간) 설정하는 방식 사용

## 9. 로컬 캐시와 리모트 캐시

서버가 사용하는 캐시 종류

1. 로컬 캐시 : 서버 프로세스와 동일한 메모리를 캐시 저장소로 사용
2. 리모트 캐시 : 별도 프로세스를 캐시 저장소로 사용

데이터 규모, 변경 빈도, 응답 시간, 처리량을 기준으로 용도에 맞게 선택해야함.

- 데이터 규모 작고 변경 빈도 낮으면 → 로컬 캐시로 충분
- 데이터 규모 크고 변경 빈도 높으면 / 배포 빈도 높으면 → 리모트 캐시 사용
- 로컬 캐시 구현 기술 : Caffeine(자바), go-cache(Go), node-cache(Node.js)
- 로컬 캐시 장점 : 서버 프로세스와 캐시가 동일한 메모리 공간을 사용하므로 데이터 접근 속도가 빠름. 외부 연동 필요하지 않아 구조 단순하게 유지 가능
- 로컬 캐시 단점 : 메모리의 물리적인 한계로 캐시 저장할 수 있는 데이터 크기에 제한 있음. 서버 프로세스 재시작하면 메모리에 존재하는 캐시 데이터 모두 삭제되어 효율 순간적으로 떨어짐.

- 리모트 캐시 구현 기술 : Redis(여러 대 redis 서버로 수평확장 가능)
- 리모트 캐시 장점 : 캐시 크기 유연하게 확장 가능해 캐시에 보관할 수 있는 데이터 규모 늘릴 수 있음. 서버 프로세스 재시작되더라도 캐시 데이터 그대로 유지되어 캐시 효율 높일 수 있음
- 리모트 캐시 단점 : 네트워크 통신으로 서버와 캐시 데이터 주고받기 때문에 속도 느림. 별도의 서버 장비와 프로세스 필요하기 때문에 시스템 구조 복잡해짐.

## 10. 캐시 사전 적재

트래픽 순간적 급증 패턴 보이면 캐시에 데이터 미리 저장하는 것도 고려할 필요 있음.

트래픽이 몰리기 전에 미리 데이터를 캐시에 넣어놓으면 캐시 적중률을 99%에 유지하여 응답시간을 안정적으로 유지할 수 있으며, db에 부하가 집중되는 현상도 방지할 수 있다.

## 11. 캐시 무효화

캐시에 저장된 데이터의 특성에 따라 (원본 데이터의 변경/삭제 시) 유효하지 않은 데이터를 적절한 시점에 캐시를 무효화해야 한다.

- 민감한 데이터 → 즉시 캐시 무효화
- 변경에 민감한 데이터는 로컬 캐시가 아닌 리모트 캐시에 보관해야함. (로컬 캐시는 다른 서버의 로컬 캐시를 변경하지 않기 때문)
- 변경에 민감하지 않고 데이터 크기 작으면 → 캐시 유효시간 설정하여 주기적으로 갱신하는 방식 사용

## 12. 가비지 컬렉터와 메모리 사용

사용이 끝난 객체를 힙 메모리에서 바로 삭제하지 않고 정해진 규칙에 따라 사용하지 않는 메모리를 찾아서 반환함.

(힙 메모리 사용량이 일정 비율 초과 → 가비지 컬렉터 실행 / 또는 일정 주기로 자동 실행)

- 개발자가 메모리를 직접 관리해야 하는 부담 줄여줌
- 코드로 메모리 관리할 수 없기 때문에 보안 이슈 줄여줌
- 가비지 컬렉터 실행되는 동안 어플리케이션 실행 일시 중단 되기 때문에 응답시간에 영향을 줌 (Stop The World)
